# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A dependency-free, drop-in script that replaces `window.console` with an on-page console panel, for mobile browsers and webviews where the dev tools aren't available. There is no test suite (`npm test` is a placeholder that exits 1). `npm run lint` runs JSHint on `js/*.js` and passes cleanly; the intentional `eval` calls (the in-page execute box) are suppressed with inline `jshint` directives.

## Commands

```
npm install      # dev deps only (sass, terser, jshint); node_modules is gitignored
npm run build    # one-shot build of everything in dist/ via scripts/build.js
npm run watch    # same build, re-run whenever js/ or scss/ changes
npm run lint     # JSHint on js/*.js
```

Building needs Node >= 20.19 (a Sass requirement). There is no dev server; open `demo.html` directly. The shipped JS is ES5 and nothing in the build transpiles it. IE support has been removed, so ES5 now only matters for old mobile/TV/webview browsers; decide that deliberately before using ES2015+ syntax.

## Build pipeline (the non-obvious part)

Source and output are different files, and the output is committed:

- **Edit only the files in `js/` and `scss/console-style.scss`.** Everything under `dist/` is generated by `scripts/build.js`, but is checked in. Run `npm run build` and commit `dist/` alongside source changes. The README CDN link points at `dist/js/console.min.js` on a git tag.
- `scripts/build.js` compiles the SCSS with Dart Sass twice (expanded -> `console-style.css`, compressed -> `console-style.min.css`). It concatenates `js/helpers.js`, `js/cl.js` and `js/main.js` (the `PARTS` list, in that order) inside one IIFE, replaces the literal placeholder `'{{consoleLogStyles}}'` (in `CL.init`, `js/cl.js`) with the compressed CSS, and writes `dist/js/console.js`. Terser then minifies that generated file, not the sources in `js/`, into `console.min.js`. The compressed Sass output is used as-is, so CSS values ship as written in the SCSS.
- **The `js/` files are fragments, not modules.** They share one scope because they are concatenated, so each file's top-level `var`s are visible to the others, and none of them is valid to load on its own at runtime. A new file must be added to `PARTS`, and order matters: `main.js` runs at load time using what the other two define.
- The CSS is escaped into the JS string literal (a quote or backslash in the CSS would otherwise break the string literal), and the result is syntax-checked with `vm.Script`, so a bad inline fails the build instead of shipping broken JS.
- Terser runs with `compress: { directives: false }`; don't remove it. The `CL.funcs` stubs are `function() {'[native code]';}`, and terser otherwise strips the lone string statement down to `function(){}`, so logging `console` or a console method would stop printing `[native code]`.
- `demo.html` loads `dist/js/console.js?200`, not the files in `js/`. Running the demo without a build, or with a stale `dist/`, shows old code.
- The demo only shows the panel if the console is not natively supported, the UA is mobile, or `?override` is on the script URL. On desktop, add `?override` to the script `src` or emulate a mobile device.

## Architecture

All runtime code is one IIFE (assembled from the three `js/` fragments) with two namespaces and some shared IIFE-scoped state.

- `Helpers` (`js/helpers.js`): DOM and utility functions (`create`, `addClass`/`removeClass`/`hasClass`, `isMobile`, `getWinH`) plus `ObjString`. `ObjString` is a modified Crockford `JSON.stringify` that prints unquoted keys, then turns `\n` into `<br>` and spaces into `&nbsp;`. It unwraps boxed primitives itself instead of patching `toJSON` onto the built-in prototypes (an earlier version did, which leaked into the host page), so don't reintroduce changes to page globals.
- `CL` (`js/cl.js`): the UI controller. `init` calls `setup` (builds the DOM), `insertRules` (injects CSS), `scriptParams` (reads the query string), `setHeight`, `toggle` and `bindEvents`. `CL.funcs` holds stub "native code" functions that are printed when the user logs `console` or `console.log`.
- `js/main.js`: the activation check (`typeof console !== 'object' || Helpers.isMobile() || CL.override()`) decides whether to run `CL.init()` and then assign `window.console` and `window.onerror`. Everything after that sits inside this `if`, including the shared `var`s.

Things that are easy to get wrong:

- **Implicit per-entry state.** `entryClass`, `isError`, `isExec`, `consoleError`, `consoleAssert` and `sym` are shared variables, not arguments. `console.error`, `warn` and `assert` set these flags and then delegate to `console.log`. `log` builds the `<li>` and calls `CL.newLog()`, which resets every flag. New console methods or entry types must follow the same set-flags -> `log` -> `newLog` flow, or flags will leak into the next entry. `executeCode` (the in-page input box) uses the same trick, setting `sym` to `>` or `<` before each `console.log` and calling `eval` on the input.
- **Output is HTML strings.** `log` builds an HTML string per argument (`CL.syntax` adds color spans using regexes over `ObjString` or `printHTML` output) and assigns it with `innerHTML`. Escaping happens in `printHTML` and the syntax regexes, so changes there can break or open up markup. String arguments are deliberately not escaped (a known issue, listed in the README), and `console.clear` relies on that to render its `<em>Console was cleared</em>` message, so escaping strings means changing that call too.
- **Sentinel `%CL%ML101417`.** `window.console.ID` and the `ID` locals in each method carry this string, and `log` tests for it with a regex. It is how logging `console` or `console.log` is detected and swapped for the `CL.funcs` stubs, which avoids dumping the real functions. Don't remove the `ID` locals or rename the sentinel without updating those checks.
- **CSS injection is a naive parser.** `insertRules` splits the minified CSS string on `}` and `{` and calls `insertRule` on `document.styleSheets[last]` (the `<style>` that `setup` appends). Only flat `selector{rules}` blocks work. `@media`, `@keyframes` and other nested at-rules in the SCSS would be mangled.
- **Query-string options** are read from the `<script>` tag's own `src` (matched by `/console(\.min)?\.js/`). `scriptParams` handles a numeric value (height), `hide`, and `timestamp`. `timestamp` is not mentioned in the README. `CL.override()` separately checks for `override`. Height must be >= 90 and <= window height - 150, otherwise it falls back to a third of the window height.
